AIチャットで「自社／他社・案件が混ざる」問題の原理と対策
日付: 2026-08-26
対象PR: https://github.com/takahiro44/torano-maki/pull/32
検証詳細: docs/chat-mix-eval-2026-08-26.txt
実装箇所: backend/app/services/agent_loop.py（SYSTEM_PROMPT）

========================================================================
0. 30秒でわかる結論
========================================================================

混ざる場所は「検索」ではなく、主に「回答を文章にまとめる段階」だった。

検索は意味が近いナレッジを複数件返す（これは仕様）。
LLM がそれらを「同じ顧客の話」として1本に繋いで書くと、
A社の予算と田中製作所の価格対応などが一つの注意点に見える。

対策は、チャットのシステムプロンプトに
「案件を混ぜるな／特定顧客の質問はその案件だけ／他社は別案件と書け」
を明示したこと。コードでナレッジを物理的にフィルタしたわけではない。

だから効くのは「本文の組み立て」。検索ヒット一覧（citations）は今も複数件出る。

========================================================================
1. 全体の流れ（どこで何が起きるか）
========================================================================

ユーザー質問
    │
    ▼
Agent Loop（agent_loop.py）
    │  system に SYSTEM_PROMPT を載せる
    │  vLLM（Qwen）へ chat/completions
    ▼
LLM が Tool を呼ぶ（例: search_knowledge）
    │
    ▼
ハイブリッド検索（意味 + 語 + RRF）
    │  confirmed ナレッジから top_k 件（だいたい5件）
    │  「似ている順」なので、A社以外も混ざるのは正常
    ▼
Tool 結果（複数ナレッジの JSON）が会話に戻る
    │
    ▼
LLM が最終回答の本文を書く  ← ★ここが混在の主因だった
    │
    ▼
アプリが citations を Tool 実行結果から別途組み立てて返す
   （本文から出典を拾わない。LLM に ID を書かせない）

ポイント:
- 検索は「候補を広く出す」部品
- 本文は「候補をどう要約・接続するか」の部品
- 混在は後者の失敗として起きやすい

========================================================================
2. なぜ混ざっていたか（原理）
========================================================================

(1) 検索は顧客フィルタをしていない
    「A社への提案で注意すべきことは？」でも、意味的に近い
    「予算」「提案」「属人化」などがヒットする。
    田中製作所の価格対応も「提案・価格」で近いので上位に入りうる。

(2) LLM は「同じテーマの箇条書き」にまとめがち
    Tool 結果に複数件あると、質問の主語（A社）に寄せて
    「A社では二重入力も…」「A社では田中さんも…」のように
    別ナレッジの事実を一つの顧客ストーリーに接続してしまう。
    これは幻覚というより「要約のやり方の癖」。

(3) 以前の SYSTEM_PROMPT は「Tool の内容だけ使え」は言っていたが
    「案件をまたぐな」は言っていなかった。
    だから複数件を使える限り、繋げて書くことが許されていた。

実測（Before）:
  Q: A社への提案で注意すべきことは？
  → 予算超過（本当に A社）に加え、二重入力・属人化（田中さん）を
    A社の注意点として本文に記載。価格指摘ナレッジも citations に混在。

========================================================================
3. 何を直したか（対策の原理）
========================================================================

SYSTEM_PROMPT に「## 案件の分離（重要）」を追加した。

やっていること（ソフト制約）:
  - 複数ヒットしても、異なる顧客・商談の事実を1話にしない
  - 複数案件は見出しで分け、会社名・状況の手がかりを先頭に書く
  - 「A社」と聞かれたら本文は A社関連だけ。他社は「別案件の参考」と明示
  - 1段落の中で会社名・金額・結果をまたがない

やっていないこと（ハード制約）:
  - 検索結果を顧客名で自動フィルタしていない
  - citations から他社を落としていない
  - DB スキーマや Tool 定義は変更していない

なぜプロンプトだけで効くか:
  Agent は最終回答を書く直前に、Tool で得た複数件を全部見ている。
  その「書き方の規則」を変えると、同じ検索結果でも
  「混ぜた要約」ではなく「分けた列挙」になる。

実測（After）:
  Q: A社への提案で注意すべきことは？
  → 本文は SalesCompass 予算超過（360万/300万/段階導入）のみ。
    田中製作所・二重入力などは「別案件」と末尾で明示。

  Q: 価格が高いと言われたとき
  → 事例1 田中製作所 / 事例2 A社 と会社名付きで分離
    （Before でも事例分けはあったが、会社名の明示が弱い）

========================================================================
4. 抽出プロンプト改善（PR #30）との関係
========================================================================

抽出側（登録時）:
  一般論を減らし、固有名詞・数値をナレッジに残す。
  → 各件の「誰の話か」が検索・回答の材料としてはっきりする。

チャット側（回答時）:
  材料が複数あっても、文章で案件をまたがない。

両方あると強いが、役割は違う。
  抽出だけ: 材料の質は上がるが、まとめ方次第でまだ混ざる
  チャットだけ: 混ざりにくくなるが、材料が抽象的だと分離の手がかりが弱い
  今回: チャット側を直接直し、混在を実証的に減らした

========================================================================
5. 限界と次に効く手（共有用）
========================================================================

限界
  - プロンプト遵守はモデル依存。温度や長文でまた混ざる可能性は残る
  - citations には検索上位がそのまま乗る（UI 上「関係しそうな件」に見える）
  - 「A社」と書いていないナレッジは、顧客限定質問でも本文に入れにくい／入れすぎる判断が曖昧

次に効く改善（やるとしたら）
  1. 検索に industry / 固有名詞フィルタや「クエリの顧客名で絞る」を足す
  2. 回答前に LLM へ渡す候補を、質問の顧客名で前処理フィルタする
  3. UI で citations を「本文で使った件」だけに絞る（いまは触った検索結果全体）

========================================================================
6. チームへの伝え方（コピペ用）
========================================================================

「AIチャットの混在は、検索が悪いというより、複数ヒットを1顧客の話に
まとめてしまう回答生成の問題だった。SYSTEM_PROMPT に案件分離ルールを入れ、
A社質問では本文をA社案件に限定し、他社は別案件と書くようにした。
検索そのものは広く返すまま。検証で Before/After を確認済み（PR #32）。」
