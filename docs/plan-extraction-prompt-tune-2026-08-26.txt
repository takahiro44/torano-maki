0. 一言でいうと
========================================================================

既存パイプライン（登録 → draft → 承認 → 探す → AIチャット）は触らない。
直すのは `backend/app/services/extraction.py` の `_SYSTEM_PROMPT` と、
必要なら user メッセージの短い指示文だけ。スキーマ・API・DB・画面は変えない。

目的: 「営業が持っている具体ノウハウ」として使える抽出にする。
一般論・抽象語・固有名詞の脱落を減らす。

見積: 修正 1.5〜2h + Before/After 検証 1.5〜2h ＝ 計 3〜4h

1. 現状の仕様（このリポジトリの事実）
========================================================================

プロンプトの置き場
  ✗ backend/app/prompts/ は存在しない
  ○ backend/app/services/extraction.py
      - `_SYSTEM_PROMPT` … システム指示（いま約30行）
      - `build_extraction_payload()` … user に JSON Schema 全文 + 入力本文

呼び出し経路（変更しない）
  画面「登録」
    → POST /ingest/text
    → process_text_to_knowledge()
    → extract_knowledge_with_sources()
    → _extract_one_chunk() / build_extraction_payload()
    → vLLM chat/completions（json_schema + thinking OFF）
    → ExtractedKnowledge（Pydantic）→ knowledge_units + embedding

検証用の別経路（本番登録せず比較できる）
  POST /ingest/text/preview
    → 同じ抽出ロジック、DB 非保存、extracted だけ返す
  ※ Before/After 比較はまずここを使う（confirmed を壊さない）

スキーマ（触らない）
  ExtractedKnowledge の列:
    title, situation, problem, judgment, action, reasoning,
    outcome, lesson, applicable_situations, limitations,
    industry, product, sales_stage, knowledge_type(=sales_knowhow 既定)
  ※ ユーザー案の learning は無い。正は lesson。

注意: experiments/knowledge-extraction/prompt.md は
  音声文字起こし検証用で、本番アプリの抽出とは別物。
  本タスクではアプリの extraction.py だけを正とする。
  実験側を揃えるのは任意・後回し。

LLM 制約（崩さない）
  - MODEL_NAME は .env の配信中 ID（例: Qwen3.8-27B-NVFP4）
  - response_format.json_schema + structured_outputs
  - chat_template_kwargs.enable_thinking = false
  - temperature 0.1 のまま（まずプロンプトだけで効かせる）

========================================================================
2. 問題の分解（何を直すか）
========================================================================

チーム指摘「ナレッジが営業側が持っているナレッジになっていない」を分解する。

A 一般論すぎる
  lesson が「顧客の話をよく聞くことが大切」レベル
B 具体性不足
  会社名・金額・製品・役職が落ちる
C CBR が形だけ
  action が「適切な提案を行った」、judgment / reasoning が空または薄い
D 言葉遣いが AI っぽい
  「〜することが有効である」「〜を図る」など教科書調に言い換え

現状 DB の confirmed 7件をざっと見ると:
  - 価格指摘・予算超過は比較的具体（固有の行動・金額が残っている）
  - lesson はまだ「〜することが有効である」型の一般化が強い（D寄り）
  - 走り書き系・短い入力では B/C が出やすい想定
  → まず A/B/D をプロンプトで抑え、C は「null 可」を維持しつつ
    埋まっている欄の中身の具体性を上げる

判定基準（レビュー用チェックリスト）

  合格の目安（1件あたり）
  - 固有名詞または数字が situation / action / lesson のいずれかに残る
    （入力にあれば。無ければ null 可）
  - lesson を読んで「明日の商談で何をするか」が想像できる
  - 入力に無い事実を足していない
  - 「傾聴が大事」「信頼関係を築く」だけの件は不合格（抽出しないか却下）

========================================================================
3. 対応方針（プロンプト3点。ロジックは最小）
========================================================================

### 3.1 修正対象ファイル

必須
  backend/app/services/extraction.py
    - `_SYSTEM_PROMPT` を差し替え／追記
    - （任意）`build_extraction_payload` の user 先頭1〜2文を具体性寄りに

やらないこと
  - 新テーブル・新 API・フロント改修
  - ExtractedKnowledge のフィールド追加
  - temperature / チャンクサイズ変更（初回イテレーションでは触らない）
  - search_text / embedding の計算式変更（抽出結果が変われば自動で追従する）

### 3.2 修正1: 具体性の必須ルール

`_SYSTEM_PROMPT` の「## ルール」を拡張する。文言の骨子:

  - 入力にある固有名詞（会社名、人名、役職、製品名）と数値（金額、人数、期間）は
    可能な限り situation / problem / action / outcome / lesson に残す
  - 一般論・当たり前の教訓だけを抽出しない
    （例: 「傾聴が大事」「信頼関係を築く」単体）
  - 抽象的な言い換えをせず、営業が実際に取った行動・発言を優先して書く
  - 「〜という考え方もある」「〜が望ましい」ではなく、
    何をしたか・何が起きたかを書く
  - 情報不足の項目は null（無理に一般論で埋めない）← 既存ルール維持

### 3.3 修正2: Few-shot（悪い例 / 良い例）

フィールド名はコードに合わせて lesson / action を使う。

  ❌ lesson: 「顧客の話をよく聞くことが大切」
  ✅ lesson: 「価格を指摘されたら値引きの前に比較軸を聞く。
              今回は保守対応の質が争点で、24時間対応と現地常駐を説明して受注した」

  ❌ action: 「適切な提案を行った」
  ✅ action: 「営業部30名だけの段階導入を出し、初年度を予算内に収める提案をした」

  ❌ title: 「提案のコツ」
  ✅ title: 「価格指摘時の比較軸確認と価値訴求の対応法」（既存の良い例に近い）

Few-shot は 2組で足りる。長くしすぎると JSON Schema と競合して
指示が薄まるリスクがある。まずは短く入れて検証し、足りなければ1組追加。

### 3.4 修正3: 抽出する／しないの境界

  抽出しない
    - 雑談・事務連絡・感情のみ（「頑張ります」）
    - 入力に根拠のない一般常識だけ
  抽出する
    - 特定の顧客・状況に対する具体行動
    - その判断理由
    - 結果（分かれば）
    - 次に同じ場面が来たときの示唆（lesson）

「1テキストから複数可」「空配列可」は既存どおり残す。
弱い一般論を無理に1件出すより、空の方がマシ、と明記する。

### 3.5 ロジック側でやってよい最小オプション（任意・2周目）

プロンプトだけで足りないときだけ検討。初回コミットには入れない。

  - title 重複除去は既にある（seen_titles）
  - 追加するなら: lesson / action が短すぎる or 禁止フレーズ辞書に当たったら
    その件を落とす薄いフィルタ（誤検知に注意。ログだけ出す方が安全）
  - temperature を 0 にする実験は検証ブランチで A/B してから

4. 実装手順（作業順）
========================================================================

Step 0 準備（15分）
  - git switch main && git pull
  - feat/extraction-prompt-tune を切る
  - いまの `_SYSTEM_PROMPT` を docs か PR 用に Before としてコピーしておく
  - uvicorn 起動、BASE_URL / MODEL_NAME 確認（/health/config）

Step 1 Before 採取（30〜45分）
  - 評価用入力を固定する（再実行で比較できるようにする）
    必須: backend/data/demo_live_inputs.txt の【1】【2】【3】
    推奨: 【4】【5】、短い走り書き【2】は一般論化しやすいので重点
  - 各入力を POST /ingest/text/preview で抽出し、
    docs/extraction-prompt-eval-2026-08-26.md（または txt）に
    「入力全文 / 抽出 JSON / 判定メモ」を残す
  - 既存 confirmed 7件もチェックリストで弱い lesson を印付け
    （再抽出の参照用。元文は evidence の excerpt または demo 文）

Step 2 プロンプト修正（45〜60分）
  - `_SYSTEM_PROMPT` に §3.2〜3.4 を反映
  - 既存の「各項目は1〜3文」「推測しない」「null 可」は残す
    （長くなりすぎて矛盾しないよう整理する）
  - ruff / 既存 ingest テストが通ることを確認
    （プロンプト文字列変更だけではテストはほぼ無影響）

Step 3 After 採取と比較（45〜60分）
  - 同じ入力で再度 /ingest/text/preview
  - 比較観点
      1. 固有名詞・数値の残存率（入力にあれば）
      2. lesson / action が「明日使える指示」になっているか
      3. 一般論だけの件が減ったか（または空になったか）
      4. 幻覚（入力に無い事実）が増えていないか ← 悪化なら即ロールバック寄りに短縮
  - 良い入力【1】が悪化していないこと（回帰チェック）

Step 4 共有と PR（30分）
  - Slack / 夕会用に Before/After を3件だけ貼る（長文はリンク）
  - PR: feat/extraction-prompt-tune
    タイトル例: `feat: 抽出プロンプトで具体的な営業ナレッジを優先する`
  - main 直コミット禁止。レビュー1人以上

6. リスクと回避
========================================================================

| リスク | 回避 |
|---|---|
| プロンプトが長くなり JSON が崩れる | Few-shot は2組まで。thinking OFF 維持。壊れたら短縮 |
| 抽出しすぎて空ばかりになる | 「情報があるエピソードは落とすな」を1行追加。空は弱い入力のみ |
| 既存の良い件が抽象化する | 【1】を回帰ケースに固定 |
| confirmed を上書きしてデモデータ消失 | preview で比較。本番登録し直すのは承認後・必要時だけ |
| 実験用 prompt.md と本番が乖離 | 本タスクの正は extraction.py。実験同期は後回し |
