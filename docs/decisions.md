## 決定の記録

### 2026-08-26 音声の文字起こしは同期リクエストで処理し、ナレッジ化と2段に分ける

- **背景 / 課題**: 商談音声を投入してナレッジ化する画面を作るにあたり、
  CLAUDE.md 6章は「音声処理はHTTPリクエスト内で完結させない」と定めている。
  だがその根拠は 2026-08-24 の検証（`faster-whisper` の `medium` をCPUで実行して
  8分50秒の音声に**7分29秒**）であり、その後 DGX Spark 上に
  OpenAI互換の音声認識サーバ（`medium` / `cuda` / `float16`）が立った。
  **同じ音声を実測して31秒**（実時間の約17倍速）。前提が変わった
- **選択肢**:
  1. CLAUDE.md どおり `jobs` テーブル + BackgroundTasks でジョブ化する
  2. 同期リクエストで処理し、待ち時間は画面の進捗表示で吸収する
  3. 文字起こしとナレッジ化を1つのAPIにまとめて一気に通す
- **決定**: **2。** `POST /ingest/audio/transcribe` は同期。
  さらに文字起こしとナレッジ化を分け、間に人の確認を挟む
  （`/ingest/audio/transcribe` → 画面で確認・修正 → 既存の `/ingest/text`）
- **理由**:
  - **`jobs` テーブルは `docker/initdb/02_schema.sql` に無い。** 追加はDDL変更で、
    4人全員が `docker compose down -v` を回すことになる（＝各自のナレッジが消える）。
    31秒の待ちを消すために払うコストとして高すぎる
  - 既存エンドポイントはすべて `def`（`async def` ではない）でスレッドプールに
    逃げるため、**31秒待ってもイベントループは止まらない。**
    検索・一覧・チャットは並行して処理される
  - **切断しても結果は失われない。** `data_sources` と `utterance_segments` は
    レスポンスを返す前に commit しており、クライアントが切れても処理は完走する
  - **文字起こしの誤りは後段のLLMでは直せない。** 欠落（14秒分の消失を実測）と
    幻覚（無い言葉が11文字混入）は、どちらも自然な文に見えるため誤りとして
    検知できない。数量表現は全モデルで正しく取れており、逆に言えば
    **壊れたら復元できない情報がそのまま入る。** 人が1回見る段を挟む価値がある
    （詳細は `experiments/stt/README.md`）
  - 2段に分けた副産物として、**ナレッジ化は既存の `/ingest/text` をそのまま使える。**
    抽出の入力は結局テキストであり、経路を2本持つとプロンプトやチャンク分割の
    改善を両方に当て続けることになる
- **見送った案とその理由**:
  - 案1: 上記のとおりDDL変更のコストが見合わない。
    なお `services/audio_ingest.py` に処理を寄せてあるので、
    **必要になった時点でこの関数を BackgroundTasks に渡すだけで移行できる。**
    同期で書いた分は捨て実装にならない
  - 案3: 文字起こしの誤りをそのまま貯めることになる。
    また抽出まで含めると待ちが2分近くになり、同期で通す前提が崩れる
- **あわせて決めたこと**:
  - 根拠（`knowledge_evidence`）は、抽出に使った原文を発話の連結文字列から
    **文字オフセットで探して実際の `utterance_segments` に紐づける。**
    テキスト投入では時刻がダミー（0.0〜0.01秒）の合成セグメントを作っているが、
    音声由来なら本物の時刻が入る。人が本文を修正して照合できない場合は、
    近い発話へ無理に寄せず従来どおり合成セグメントに退避する
    （根拠として嘘をつくより、時刻が無い方がまし）
  - 話者は `unknown` で入れる。`faster-whisper` は話者分離をしないため、
    `営業` などと決め打ちすると後で話者分離を入れたときに嘘のデータが残る
- **覆すとしたら**: 扱う音声が20分を超えるのが常態になったとき（待ちが70秒超）、
  複数ファイルの一括投入が要るとき、文字起こし中に他の操作をしたい要望が出たとき。
  そのときは案1へ移す

### 2026-08-26 デモ音声の台本はモデルに書かせ、下書きと正の台本を分ける

- **背景 / 課題**: 商談台本を ChatGPT に書かせるようになったが、
  出力は**スキーマが合っていても細部が毎回ぶれる**（コードブロックで囲まれる、
  話者名が「営業」と `Sales` で混ざる、稀に1発話が API の 4000 bytes 上限を超える）。
  さらに台本は**数本をまとめた1つのJSON**で来るため、束ね方も毎回同じとは限らない。
  そのたび手で直していては、台本が増えるほど人手が増える
- **選択肢**:
  1. 台本JSONを手で整えてから `scripts/` に置く（これまで）
  2. `generate_tts.py` に崩れの吸収を足す
  3. 取り込み（`import_script.py`）を分け、`make_audio.py` で一気に通す
- **決定**: **3。** `drafts/`（モデルの出力そのまま・git管理外）と
  `scripts/`（検証・正規化済みで、これが正・**台本1本＝1ファイル**）を分ける。
  `uv run make_audio.py drafts/<下書き>.json` で、束に入っている本数ぶん音声が出る
- **理由**:
  - **合成は課金される。** 直せる崩れは吸収し、人が直すべきものは
    **API を1回も呼ばないうちに**落とす方が安い（`--dry-run` で検証だけもできる）
  - 声と人物像は聴いてから調整するため、`scripts/` は人が手を入れる場所として残す。
    古い下書きを再実行してその調整が消えないよう、内容が変わる上書きは
    `--force` が要る
  - 合成の作り方（プロンプト・分割・結合・音量調整）は `generate_tts.py` のまま。
    取り込みを別ファイルにしたのは、**検証済みの合成手順を触らずに済ませる**ため
  - **束は受け取り方を1つに決めない。** 配列・`scripts` キー・名前をキーにした
    オブジェクトのどれでも受ける。モデルの書き方に合わせて台本を出し直させるより、
    受け側で吸収する方が安い。一方 `scripts/` は1本1ファイルに開く
    （合成・再開・出力先が台本単位のため、束のまま持つと全部が巻き添えになる）
  - **束のうち1本でも検証に落ちたら、その束は1本も書かない。**
    3本目で落ちて1・2本目だけ `scripts/` に残ると、束と取り込み済みが食い違う
  - 台本の指紋（sha256）を `output/<台本名>/script.sha256` に残し、
    **台本が変われば全パートを作り直す。**
    古い `part_*.wav` が結合に混ざると、音声だけ古いことに誰も気づけない
- **見送った案とその理由**:
  - 案1: 台本が増えるほど手作業が増える。自動化の意味が無い
  - 案2: 実測で選んだ合成手順に、モデル出力の都合が混ざる。
    台本の形式が変わるたびに合成の本体を触ることになる
- **注意**: 本文には NFKC をかけない。「ですか？」の全角疑問符まで半角になり、
  読み上げの抑揚が変わる。正規化するのは空白だけにしてある
- **覆すとしたら**: 台本を人が書くようになった場合。そのときは `drafts/` を廃し、
  `scripts/` を直接編集すればよい（`generate_tts.py` は今までどおり動く）

### 2026-08-25 Lexical Search に PostgreSQL 標準の全文検索ではなく `pg_trgm` を使う

- **背景 / 課題**: ベクトル検索だけでは「同じ顧客の情報を漏れなく集める再現率」が
  低いことが分かっていた（`docs/setup-notes.md` 2026-08-21）。
  語の一致による検索を足して RRF で統合したい。
  当初の指示は「PostgreSQL標準の全文検索（`tsvector` / `ts_rank`）を使う」だった
- **選択肢**:
  1. PostgreSQL 標準の全文検索（`tsvector` / `tsquery` / `ts_rank`）
  2. 既に有効化済みの `pg_trgm` の `word_similarity()`
  3. PGroonga / ParadeDB など日本語対応の拡張を追加する
  4. MeCab / Sudachi で Python 側で分かち書きしてから 1 を使う
- **決定**: **2 の `pg_trgm` を使う。**
- **理由**: **標準の全文検索は日本語で機能しないことを実測で確認した。**
  PostgreSQL の default parser は日本語を分かち書きできず、句点までを
  丸ごと1トークンにする。PostgreSQL 17.11 での実測:

  ```
  to_tsvector('simple', '基幹システム保守サービスの導入事例')
    → '基幹システム保守サービスの導入事例':1        ← 1トークン

  to_tsvector(...) @@ to_tsquery('simple', '基幹システム')   → false
  ```

  `ts_rank` で並べる以前に `tsquery` がヒットしない。`pg_ts_config` に
  日本語の設定は存在せず、分かち書き器も標準には無い。
  **これは調整の問題ではなく、標準構成では成立しないということ。**

  `pg_trgm` は文字トライグラムを見るため分かち書きを必要とせず、日本語で動く。
  そして**新しい依存の追加ではない**。`docker/initdb/01_init.sql` で有効化済みで、
  `idx_knowledge_search_trgm` も既に DDL にある。DB の作り直しも不要だった。

  シード16件での実測（Recall@5）:

  | | Semantic | Lexical | Hybrid |
  |---|---|---|---|
  | 平均 | 0.97 | 0.62 | **1.00** |
  | 「A社」（同一顧客4件の再現率） | 0.75 | 1.00 | **1.00** |

  Lexical 単独は弱いが、**Semantic が苦手なところだけを正確に補う。**
  これが RRF で統合する価値そのもの
- **見送った案とその理由**:
  - **1（標準全文検索）**: 上記のとおり日本語で成立しない。
    **なお `ts_rank` は BM25 ではない。** 実装していないが、
    仮に使ったとしても「BM25を実装した」と書いてはいけない
  - **3（PGroonga 等）**: 日本語全文検索としては本命だが、Docker イメージの
    差し替えが必要で、4人分の環境再現をやり直すコストが MVP に見合わない
  - **4（MeCab / Sudachi）**: Python 側に辞書込みの依存が増える。
    `pg_trgm` で足りている段階で入れる理由がない
- **覆すとしたら**: ナレッジが数百件を超えて `word_similarity` の精度が頭打ちになるか、
  「語の重みづけ（頻度が低い語ほど重要）」が必要になったとき。
  その時点で 3 を検討する。差し替えは `services/search.py` の
  `lexical_search()` の中だけで完結するようにしてある

### 2026-08-25 スコアを直接足さず RRF で統合する

- **背景 / 課題**: Semantic と Lexical の結果を1つの順位にまとめる必要がある
- **決定**: **Reciprocal Rank Fusion（`RRF_score(d) = Σ 1 / (k + rank(d))`、k=60）**
- **理由**: 2つのスコアは意味もスケールも違う。e5 のコサイン類似度は
  0.78〜0.88 の狭い範囲に固まるのに対し、`word_similarity` は 0.0〜0.9 に広がる。
  **足し算すると値域の広い Lexical が常に勝ってしまう。**
  正規化して足す案もあるが、正規化の基準（母集団の最大・最小）が
  クエリごとに変わるため安定しない。順位だけを使えばこの問題が消える。
  k=60 は Cormack et al. (2009) の値
- **見送った案とその理由**: 重み付き加算（`α * semantic + (1-α) * lexical`）。
  α をクエリごとに調整する必要が出て、調整の根拠を残せない
- **覆すとしたら**: Reranker を入れて最終順位をそちらに任せるようになったとき。
  その場合も候補集合を作る段階では RRF が有効

### 2026-08-25 語彙検索は確信が持てないときに何も返さない

- **背景 / 課題**: `word_similarity` は長い自然文クエリだと全件が 0.06〜0.38 の
  横並びになり、**どれが1位になるかがほぼ運**になる。
  これを RRF に流したところ、Semantic が正しく出していた1位が押し出され、
  既存の回帰テスト（`test_search_quality.py`）が実際に落ちた
- **決定**: **`LEXICAL_MIN_SIMILARITY = 0.4` 未満は Lexical 側が何も返さない。**
- **理由**: 実測するとスコアに明確な溝がある。

  ```
  クエリ全体が一致  0.529〜0.857（2位との差も大きい）
  ------------------ 0.4 ------------------
  一部だけが一致    0.385以下（2位との差が小さく、順位が実質ランダム）
  ```

  下側は「A社の導入予定」で『A社の』だけが一致しているような状態。
  **Semantic のスコアと違い、こちらは閾値が機能する。**
  e5 は無関係でも 0.78 程度出るため絶対値で判定できないが、
  trgm は無関係なら 0.0 になる（「今日の天気」で全件 0.0 を実測）。
  **中途半端に反応するより黙る方が、統合後の結果が良くなる**
- **覆すとしたら**: ナレッジが増えて 0.4〜0.5 帯にも正しい一致が出てくるようになったとき。
  `tests/test_search.py` の比較評価で劣化を確認しながら下げること


### 2026-08-24 音声認識は `faster-whisper` の `medium` をCPUで使う

- **背景 / 課題**: DGX Spark は ARM64 + Blackwell のため、音声認識ライブラリの
  CUDA対応検証に時間を使うリスクが高い。一方、文字起こしは欠落や幻覚があると
  後段のLLMでは安全に復元できないため、モデル名だけでなく実測で選ぶ必要があった
- **選択肢**: `faster-whisper` の `small` / `medium` / `large-v3` を、
  用語集とVADの有無を変えてホストPCのCPU（`int8`）で実行する
- **決定**: **`medium` + 用語集 + VADなし**を初期構成として採用する。
  音声認識の呼び出し口は1つに集約し、製品名は製品マスタを使った後処理で補正する
- **理由**:
  - 8分50秒のデモ音声を7分29秒（実時間の1.2倍速）で処理できた
  - CER 3.1%、欠落0字で、納期・代替・新人・FAX・Excelをすべて正しく取得した
  - 数量表現9種は全モデルで一致し、復元できない数値情報が壊れていなかった
  - 非同期ジョブ前提なので、リアルタイム処理でなくても許容できる
- **見送った案とその理由**:
  - `small`: 用語集を与えても業務用語を取得できず、CER 5.7%だった
  - `large-v3`: CER 7.3%で最も遅く、存在しない文言も生成した
  - VADあり: 14秒分・41字の発話が欠落したため、既定で無効にする
  - DGX上のGPU実行: ARM64 + CUDAの対応検証より、CPUで実用速度を得る方が早く確実
- **覆すとしたら**: 実際の商談録音で欠落・幻覚・処理待ちが許容範囲を超えた場合、
  またはDGX上で安定して高速化できる構成が確認できた場合。今回の音声はTTS合成のため、
  実音声を入手した時点で同じ指標（CER・欠落・業務用語・数量）を再評価する

### 2026-08-21 PostgreSQL のみ Docker 化し、アプリ本体はホストで動かす

- **背景 / 課題**: Mac 2人 / Windows 2人の混在チーム。うち2人は Docker に不慣れ。
  PostgreSQL + pgvector をネイティブに入れる手順はOSごとに大きく異なり、
  4人が同じ環境を再現するのが難しい
- **選択肢**:
  1. 全部ネイティブ
  2. 全部 Docker（DB + FastAPI + フロントエンド）
  3. DBのみ Docker、アプリはホスト
- **決定**: **3**
- **理由**:
  - PostgreSQL + pgvector は「導入手順がOS依存で、一度動けば触らない」ため
    コンテナ化の利得が最も大きい
  - 逆に FastAPI / Vite は**コード修正のたびに再ビルド待ちが発生する**方が損失が大きい。
    `--reload` と HMR の即時反映を優先する
  - Docker に不慣れな2人が覚えるコマンドが `docker compose up -d` だけで済む
- **見送った案とその理由**:
  - 案1（全部ネイティブ）: Postgres と pgvector の導入で2人が確実に詰まる
  - 案2（全部Docker）: ハッカソンの反復速度を犠牲にする。
    また Ollama を ARM64 + CUDA のコンテナで動かす検証コストが高い
- **覆すとしたら**: デモを別マシンで再現する必要が出た場合、
  そのときだけ backend / frontend の Dockerfile を追加する

### 2026-08-21 Ollama は DGX Spark にネイティブ導入し、LANで共有する

> ⚠️ **この決定は同日中に覆った。**実機の DGX Spark では Ollama ではなく vLLM が動いていたため。
> 下の「2026-08-21 LLM推論は Ollama ではなく DGX 上の vLLM を使う」を参照。
> LANで共有する方針と、その注意点（認証なし・1台を4人で共有）は変わらない。

- **背景 / 課題**: GPUは貸し出しのDGX Spark 1台のみ。4人で共有する必要がある
- **決定**: DGX にネイティブインストールし、`OLLAMA_HOST=0.0.0.0:11434` でLANに公開。
  各自の `.env` の `OLLAMA_BASE_URL` からDGXを指す
- **理由**:
  - ARM64 + CUDA のコンテナ内GPU利用は検証コストが高く、ネイティブなら導入が1コマンド
  - Mac には CUDA が無いため、そもそも各自のローカルでGPU推論はできない
- **注意**:
  - **認証なしでLANに開く設定**なので、会場のネットワーク内に限定する
  - **1台を4人で共有するため、全員が同時に重いモデルを叩くと詰まる。**
    開発は各自ローカルの軽量モデル、デモはDGX、という切り分けを推奨
- **覆すとしたら**: 同時アクセスで実用にならない場合、リクエストの直列化か
  デモ担当のみDGXを使う運用に変える

### 2026-08-21 埋め込みは `multilingual-e5-large` / 1024次元に確定

- **背景 / 課題**: 次元数が決まらないと `vector(N)` を定義できず、
  スキーマ・DB・検索のすべてが着手できない状態が続いていた

  **各自のPCのCPUで実行する**
- **なぜCPUか**: DGX Spark で動いているのは vLLM で、固定モデルを配信しており
  埋め込みモデルを載せられない（`/v1/embeddings` は404）。

  **検索1回につき短い文を1つベクトル化するだけ**。GPUが要る場面がない

  | 処理 | 頻度 | CPUでの体感 |
  |---|---|---|
  | Knowledge 20件の埋め込み | 初回投入時に1回 | 数秒 |
  | 検索クエリの埋め込み | 検索ごとに1回 | 0.1〜0.3秒程度 |

- **見送った案**: `cl-nagoya/ruri-v3-310m`（768次元・約600MB）。

- **覆すとしたら**: 精度が出ない、またはCPUが遅くて開発の邪魔になった場合。

  **次元数は3箇所に書かれているので、すべて揃えて直すこと。**
  1箇所でも漏らすと、ベクトルを挿入する瞬間まで気づけない。

  | # | ファイル | 直す箇所 |
  |---|---|---|
  | 1 | `docker/initdb/02_schema.sql` | `vector(1024)` |
  | 2 | `backend/app/config.py` | `DEFAULT_EMBEDDING_MODEL` / `DEFAULT_EMBEDDING_DIM` |
  | 3 | `.env`（各自） | `EMBEDDING_MODEL` / `EMBEDDING_DIM` |

  そのうえでDBを作り直す。

  ```bash
  docker compose down -v && docker compose up -d
  ```

  最後に `/health/db` の `embedding_dim_matches` が `true` であることを確認する。

  なお `.env.example` を変えても各自の `.env` は自動更新されないため、

  作り込む前に判断すること

### 2026-08-21 LLM推論は Ollama ではなく DGX 上の vLLM を使う

- **背景 / 課題**: 実機の DGX Spark に接続したところ、動いていたのは Ollama ではなく

  - `.env` の項目名を **`BASE_URL` / `MODEL_NAME`** に統一する。

- **理由**:
  - `OLLAMA_BASE_URL` という名前に vLLM の URL が入っている状態は、

  - **JSON Schema による出力制約が効かない。**

- **未決**: 上記への対処を、(1) GPU担当に vLLM 側で構造化出力を有効化してもらう、
  (2) プロンプト + パース + リトライで妥協する、(3) 抽出用に別モデルを立てる、

- **覆すとしたら**: DGX 側のサーバ構成が変わった場合。`.env` の項目名は
