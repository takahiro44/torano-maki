### 音声認識の候補と注意点

DGX Spark は ARM64 + Blackwell。**x86_64 向けのビルド済みパッケージが
使えない可能性があり、ここで時間を溶かすリスクが最も高い。**

- 検証にタイムボックスを設け、動かなければ撤退する
- 撤退先（CPU実行 / テキスト入力のみ）を先に決めておく
- CLAUDE.md 6章の「音声認識の呼び出し口を1つの関数に集約する」は、

## 決定の記録

### 2026-08-21 PostgreSQL のみ Docker 化し、アプリ本体はホストで動かす

- **背景 / 課題**: Mac 2人 / Windows 2人の混在チーム。うち2人は Docker に不慣れ。
  PostgreSQL + pgvector をネイティブに入れる手順はOSごとに大きく異なり、
  4人が同じ環境を再現するのが難しい
- **選択肢**:
  1. 全部ネイティブ
  2. 全部 Docker（DB + FastAPI + フロントエンド）
  3. DBのみ Docker、アプリはホスト
- **決定**: **3**
- **理由**:
  - PostgreSQL + pgvector は「導入手順がOS依存で、一度動けば触らない」ため
    コンテナ化の利得が最も大きい
  - 逆に FastAPI / Vite は**コード修正のたびに再ビルド待ちが発生する**方が損失が大きい。
    `--reload` と HMR の即時反映を優先する
  - Docker に不慣れな2人が覚えるコマンドが `docker compose up -d` だけで済む
- **見送った案とその理由**:
  - 案1（全部ネイティブ）: Postgres と pgvector の導入で2人が確実に詰まる
  - 案2（全部Docker）: ハッカソンの反復速度を犠牲にする。
    また Ollama を ARM64 + CUDA のコンテナで動かす検証コストが高い
- **覆すとしたら**: デモを別マシンで再現する必要が出た場合、
  そのときだけ backend / frontend の Dockerfile を追加する

### 2026-08-21 Ollama は DGX Spark にネイティブ導入し、LANで共有する

> ⚠️ **この決定は同日中に覆った。**実機の DGX Spark では Ollama ではなく vLLM が動いていたため。
> 下の「2026-08-21 LLM推論は Ollama ではなく DGX 上の vLLM を使う」を参照。
> LANで共有する方針と、その注意点（認証なし・1台を4人で共有）は変わらない。

- **背景 / 課題**: GPUは貸し出しのDGX Spark 1台のみ。4人で共有する必要がある
- **決定**: DGX にネイティブインストールし、`OLLAMA_HOST=0.0.0.0:11434` でLANに公開。
  各自の `.env` の `OLLAMA_BASE_URL` からDGXを指す
- **理由**:
  - ARM64 + CUDA のコンテナ内GPU利用は検証コストが高く、ネイティブなら導入が1コマンド
  - Mac には CUDA が無いため、そもそも各自のローカルでGPU推論はできない
- **注意**:
  - **認証なしでLANに開く設定**なので、会場のネットワーク内に限定する
  - **1台を4人で共有するため、全員が同時に重いモデルを叩くと詰まる。**
    開発は各自ローカルの軽量モデル、デモはDGX、という切り分けを推奨
- **覆すとしたら**: 同時アクセスで実用にならない場合、リクエストの直列化か
  デモ担当のみDGXを使う運用に変える

### 2026-08-21 マイグレーションツールを導入せず、DBは作り直す

- **背景 / 課題**: 4人がスキーマを触る。Alembic を入れるとマイグレーション
  ファイルの衝突とレビューコストが発生する
- **決定**: 初期はマイグレーションツールを入れず、スキーマ変更時は
  `docker compose down -v && docker compose up -d` で作り直す（データは捨てる）
- **理由**: ハッカソン期間中は**蓄積データより開発速度の方が価値が高い**。
  デモ用データは投入スクリプトで再現できるようにしておけば足りる
- **覆すとしたら**: 捨てたくないデータ（デモ用に作り込んだナレッジなど）が
  出てきた時点で Alembic を導入する。**その判断はチームで行う**

### 2026-08-21 main の取り込み手順を明文化する（CLAUDE.md 4.9 / 4.10）

- **背景 / 課題**: 4人がそれぞれ Claude Code で並行作業する構成では、
  以下が事故につながることが分かった
  1. feature branch 上で `git pull` しても `main` の変更は入らないが、
     入ったつもりになりやすい
  2. `pull` しただけでは動かない場合がある（`uv sync` / `npm ci` /
     DB作り直し / `.env` の手動更新が必要）
  3. **`.env` は `.gitignore` されているため、`.env.example` が変わっても
     自分の `.env` は自動更新されない。** 症状が接続エラーとして現れ、
     原因を特定しにくい。実際にポートを5432→5433に変えた際に該当した
  4. **CLAUDE.md はセッション開始時にしか読まれない。**
     ルールを更新しても、起動中の Claude Code は古い内容で動く
  5. ブランチを確認せずに編集を始め、`main` へ直接コミットする事故が
     実際に発生した（4.2の禁止事項に該当）
- **決定**: CLAUDE.md に以下を追加する
  - 4.9 に「`pull` は `main` の上でだけ使う」「取り込むタイミング」を明記
  - **4.10「取り込んだ後の確認」を新設**し、変更されたファイルごとに
    必要な作業を表で示す
  - 4.3 にブランチ確認を毎回行う旨を追記
  - 8章に「CLAUDE.md 変更時は Claude Code の再起動が必要」を追記
  - **マージした人が「何をすべきか」までチームに伝える**運用を明記
- **理由**: Claude Code は短時間で大きな差分を作るため、
  取り込みを先延ばしにするとコンフリクトの解消コストが急激に上がる。
  また「マージしました」だけの共有では、各自が差分を読んで判断することになり、
  必ず誰かが取りこぼす。**マージ側が手順まで伝える方が確実で安い**
- **覆すとしたら**: マイグレーションツールを導入すれば
  「DBを作り直す」手順は不要になる。その時点で 4.10 の表を更新する

### 2026-08-21 PostgreSQL の公開ポートを 5433 にする

- **背景 / 課題**: ネイティブのPostgreSQLが動いている環境では、Windowsだと
  Dockerと両方が5432をLISTENできてしまい、「ポート使用中」エラーが出ないまま
  ホストからの接続がネイティブ側に吸われる。
  症状が「認証失敗」として現れるため、ポートの問題だと気づきにくい
- **決定**: 既定を **5433** にする
- **理由**: 標準ポートを使う利点より、**4人のうち誰か1人でもネイティブPostgreSQLを
  入れていたときに originが分かりにくい形で詰まるコスト**の方が大きい。
  ポートを変えるコストはゼロ
- **覆すとしたら**: 特にない。5433が埋まっている環境があれば各自 `.env` で変える

### 2026-08-21 sentence-transformers を任意の依存グループに分ける

- **背景 / 課題**: `sentence-transformers` は PyTorch を引き連れ、
  各PCで3〜4GBになる。Mac/Windowsで導入の挙動が異なり、
  環境構築に不慣れなメンバーが詰まるリスクがある
- **決定**: 既定の依存には含めず、`ml` グループに分離する

  ```bash
  uv sync              # 通常
  uv sync --group ml   # 埋め込みを担当する人だけ
  ```

- **理由**: 埋め込みを触らないメンバーに3〜4GBの導入を強制する必要がない。
  詰まる人数を減らせる
- **見送った案**: 埋め込みもOllamaに任せる案。各PCから機械学習ライブラリを
  完全に排除できる利点があるが、CLAUDE.md 3章で合意済みのスタックから
  外れること、DGX 1台への依存が増えることから、まずは現行案で進める
- **覆すとしたら**: **Macの2人が torch の導入で詰まった場合、迷わず
  Ollama の埋め込み（`bge-m3` など）に切り替える。** その場合は
  チームで合意のうえ、ここに追記する
- **2026-08-21 追記**: この退避策は使えなくなった。DGX で動いているのは vLLM で、
  `/v1/embeddings` を持たない（404）。torch で詰まった場合の代替は別途考える必要がある

### 2026-08-21 `.gitattributes` で改行コードを統一する

- **背景 / 課題**: Mac 2人 / Windows 2人。コンテナ内で実行される `.sh` / `.sql` が
  CRLF だと、原因の分かりにくい起動エラーになる
- **決定**: `.gitattributes` で `.sh` / `.sql` / `.yml` / Dockerfile を LF に強制する
- **理由**: 混在環境では改行コードの事故が起きてから原因を特定するのに時間がかかる。
  仕組みで防ぐ方が安い
- **補足**: `.env` の CRLF は Docker Compose v5.1.0 が正しく処理することを
  検証済み（`docs/setup-notes.md` 参照）

### 2026-08-21 LLM推論は Ollama ではなく DGX 上の vLLM を使う

- **背景 / 課題**: 実機の DGX Spark に接続したところ、動いていたのは Ollama ではなく
  **vLLM 0.22.1rc1 の OpenAI互換API**（`http://<DGX>:8080/v1`）だった。
  公開モデルは `DiffusionGemma-NVFP4`（実体 `diffusiongemma-26B-A4B-it-NVFP4`、
  `max_model_len` 262144）。GPUは貸し出しであり、こちらでサーバを選べない
- **決定**:
  - LLM推論は DGX 上の vLLM（OpenAI互換）を叩く。Ollama は使わない
  - `.env` の項目名を **`BASE_URL` / `MODEL_NAME`** に統一する。
    `BASE_URL` は末尾の `/v1` まで含める（OpenAI互換クライアントの慣例に合わせるため）
- **理由**:
  - `OLLAMA_BASE_URL` という名前に vLLM の URL が入っている状態は、
    経緯を知らないメンバーが必ず誤読する
  - 推論サーバを今後また差し替えられても、名前が実態と食い違わない
- **確認したこと**（2026-08-21、`curl` で実測）:
  - `GET /v1/models` → 200。`POST /v1/chat/completions` → 日本語で正常に応答
  - **`POST /v1/embeddings` → 404。** 埋め込みはこのサーバから取得できないため、
    sentence-transformers をローカルで動かす方針（3章）を維持する
  - **JSON Schema による出力制約が効かない。**
    `response_format: {"type":"json_schema"}` も vLLM 固有の `guided_json` も無視され、
    指定していないキー名やコードフェンス付きのテキストが返る。
    拡散系モデルのため guided decoding の経路に乗っていない可能性が高い
- **これによって崩れる前提**: CLAUDE.md 6章の
  「Pydanticの JSON Schema をそのまま LLM に渡してスキーマを1箇所にまとめる」。
  Pydanticモデルを単一の源にする方針自体は維持できるが、
  **出力を強制できない以上、パースとバリデーションとリトライを自前で持つ必要がある**
- **未決**: 上記への対処を、(1) GPU担当に vLLM 側で構造化出力を有効化してもらう、
  (2) プロンプト + パース + リトライで妥協する、(3) 抽出用に別モデルを立てる、
  のどれにするか。**まず (1) を確認してから決める**
- **覆すとしたら**: DGX 側のサーバ構成が変わった場合。`.env` の項目名は
  プロバイダ非依存にしてあるので、値の差し替えだけで済むはず
