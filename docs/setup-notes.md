## 記録

### 2026-08-24 Hugging Face からのモデル取得が途中で切れる

- **やろうとしたこと**: `faster-whisper` のモデルを取得する
  （`medium` 1.5GB / `large-v3` 2.9GB）
- **起きたこと**: ダウンロードが途中で切断される。2回発生した

  ```
  LocalEntryNotFoundError: Got: ConnectError: [WinError 10054]
  既存の接続はリモート ホストに強制的に切断されました。

  httpx.RemoteProtocolError: Server disconnected without sending a response.
  ```

- **原因**: 未認証リクエストは帯域が絞られるため、大きいファイルほど切れやすい。
  「`HF_TOKEN` を設定すると速い」という警告が実際に出る
- **解決策**: **単に再試行する。** `snapshot_download` は取得済みの分を再利用するので、
  途中から再開される。`large-v3` は再試行1回・263秒で完了した。
  何度も切れるなら再試行をループで回すとよい
- **注意**: `HF_TOKEN` を設定する場合、**トークンをコミットしないこと**（CLAUDE.md 4.2）

### 2026-08-24 文字起こし環境で分かったこと（Windows 11 / x86_64 / 8コア / 32GB）

**`faster-whisper` は導入が軽い。** 詰まりやすい箇所を2つ回避できている。

| 項目 | 内容 |
|---|---|
| PyTorch | **不要**（CTranslate2 + onnxruntime）。`.venv` は 249MB |
| ffmpeg のバイナリ | **不要**（PyAV を同梱しているため） |
| モデルの置き場 | `~/.cache/huggingface`。リポジトリには残らない |
| 速度 | `medium` / `int8` で実時間の約1.2倍速 |

- 埋め込み用の `sentence-transformers`（PyTorch で3〜4GB）とは別物なので、
  **もう一組 torch を入れる必要はない**
- Windows では HF キャッシュの symlink 警告が出るが**無害**。
  開発者モードが無効なだけで、動作に影響しない（重複分のディスクは余計に使う）
- モデルの実サイズ: `small` 約0.5GB / `medium` 1.5GB / `large-v3` 2.9GB。
  **`large-v3` は精度が悪く遅かったので入れる必要はない**（`docs/decisions.md`）


### 2026-08-21 ⚠️ e5 の類似度スコアは絶対値で判断できない

**検索実装をする人は先に読むこと。**

- **やろうとしたこと**: `multilingual-e5-large` で日本語のナレッジ6件を埋め込み、
  自然文で検索して妥当な結果が返るか確認する
- **結果**: 妥当な結果が返る。ただし**スコアの読み方に注意が必要**と分かった

  | クエリ | 1位のスコア | 2位との差 |
  |---|---|---|
  | 値引きを求められたら | 0.868 | 0.056 ✅ |
  | サポート体制を重視する顧客 | 0.849 | 0.013 ✅ |
  | サポートを気にする顧客への対応 | 0.830 | **0.0002** ⚠️ |

- **分かったこと**:
  1. **スコアは 0.78〜0.88 の狭い範囲に固まる。**
     「0.9以上を関連ありとみなす」のような**絶対値のしきい値は機能しない。**
     順位（相対的な差）だけが意味を持つ
  2. **無関係な項目でも 0.78 程度は出る。** 低スコアだから無関係とは言えない
  3. 抽象的なクエリだと上位の差が 0.0002 まで縮まり、**順位が実質ランダム**になる。
     件数が少ないうちは特に起きやすい
- **検索を実装するときの指針**:
  - しきい値で足切りせず、`top_k` 件を返して人間に選ばせる
  - スコアをUIに出すなら「参考値」であることが分かる見せ方にする
  - 固有名詞（顧客名・製品名）の検索はベクトルだけだと弱い。
    `pg_trgm` のインデックス（`idx_knowledge_content_trgm`）を張ってあるので、
    必要なら併用する
- **性能（CPU / Windows x86_64）**: 6件の埋め込みが約0.4秒（モデル読み込み後）、
  検索1回が約0.2秒。**この規模ではCPUで十分**

### 2026-08-21 ベクトル検索は「同じ顧客の情報を漏れなく集める」のが弱い

15件のダミーデータでの評価結果（事前に固定した10問で **10/10 一致**）と、
そこで見えた弱点。

- **良好だったこと**
  - 固有名詞を含む具体的なクエリ（B社、CloudLedger、東都物流など）は
    該当項目が1位
  - 似た話題で結論が違う組（値引き2件、サポート2件）も、
    状況に合った方が1位になる
- **弱点1: 同じ顧客の全情報を集める再現率**
  「A社」という単語だけで検索すると、上位3件はA社だが4〜5位にB社・C社が混入し、
  **A社のセキュリティに関する項目は上位5件から漏れた**。
  1件を探す精度より、**漏れなく集める再現率**に問題が出る
- **弱点2: 特徴的な語に引きずられる**
  「情報システム部がしっかりしている会社」で検索すると、
  意図した「標準サポートで十分」ではなく、
  **「情報システム部の佐藤さん」を含む別のナレッジ**が1位になった。
  クエリ中の特徴語が、無関係なレコードの同じ語に引き寄せられる
- **対処の方針**: `pg_trgm` のインデックス（`idx_knowledge_content_trgm`）を
  張ってあるので、**キーワード一致の加点とベクトル順位を統合する
  ハイブリッド検索**が有効。次段階で検討する
- **無関係なクエリの扱い**: 「今日の天気」でも5件返り、1位のスコアは0.765。
  一方、有効な固有名詞検索でも0.796程度のことがあるため、
  **単純なしきい値で足切りすると有効な検索まで落とす。**
  画面側で「該当が無くても近い順に表示します」と明記する方針にした

### 2026-08-21 ⚠️ ネイティブPostgreSQLとのポート競合が「エラーなし」で起きる

**このリポジトリが既定で5432ではなく5433を使っている理由。**

- **やろうとしたこと**: バックエンドから `localhost:5432` のDBコンテナに接続する
- **起きたこと**: コンテナは healthy、コンテナ内の `psql` では接続できるのに、
  ホストからの接続だけが失敗する

  ```
  FATAL: ユーザー"torano"のパスワード認証に失敗しました
  ```

- **原因**: ホスト側でネイティブのPostgreSQLが5432で動いていた。
  **Windowsでは Docker とネイティブPostgreSQLの両方が5432をLISTENでき、
  「ポート使用中」エラーが出ない。** その状態でホストから接続すると
  ネイティブ側に吸われる。そちらに `torano` ユーザは存在しないため認証エラーになる

  ```
  $ netstat -ano | findstr :5432
  TCP  0.0.0.0:5432  LISTENING  18632   → com.docker.backend.exe
  TCP  0.0.0.0:5432  LISTENING   8080   → postgres.exe      ← これ
  ```

- **解決策**: 既定のポートを **5433** に変更した
  （`docker-compose.yml` / `.env.example` / `backend/app/config.py`）
- **注意**: 通常のポート競合と違い**エラーメッセージが「認証失敗」になる**ため、
  ポートの問題だと気づきにくい。認証エラーが出たらまず
  `netstat -ano | findstr :5433`（Macは `lsof -i :5433`）で
  何が掴んでいるか確認すること

### 2026-08-21 初期化SQLを追記しても反映されない

- **やろうとしたこと**: `docker/initdb/` にSQLを置いてDBを初期化する
- **起きたこと**: 一度起動した後にSQLを追記しても、再起動しただけでは実行されない
- **原因**: `/docker-entrypoint-initdb.d` のスクリプトは、
  **データディレクトリが空のとき（＝ボリューム新規作成時）にしか実行されない**仕様
- **解決策**: ボリュームごと作り直す

  ```bash
  docker compose down -v && docker compose up -d
  ```

  `-v` を付け忘れるとボリュームが残るため、何度やっても反映されない。
  **`-v` はデータを完全に削除するので、実行前に消えて困るデータがないか確認すること。**

### 2026-08-21 Windows の CRLF が `.env` に影響しないか検証

- **懸念**: Mac 2人 / Windows 2人の混在環境。Windowsで `.env` がCRLFになると、
  値の末尾に `\r` が混入して接続文字列が壊れる可能性がある
- **検証結果**: **問題なし。** Docker Compose v5.1.0 はCRLFの `.env` を正しく解釈し、
  値に `\r` は混入しなかった
- **ただし**: コンテナ内で実行される `.sh` / `.sql` はCRLFだと壊れるため、
  `.gitattributes` でLFを強制している。このファイルは消さないこと

### 2026-08-21 `.gitignore` の `models/` がスキーマ定義を巻き込む

- **起きたこと**: 大容量ファイル除外のつもりで `models/` と書くと、
  **`backend/app/models/`（Pydanticスキーマ定義）まで除外される**
- **原因**: 先頭に `/` が無いパターンは、どの階層のディレクトリにもマッチする
- **解決策**: リポジトリ直下だけを対象にする

  ```
  /models/
  /data/
  /uploads/
  /outputs/
  ```

- **確認方法**: `git check-ignore -v <パス>` で、意図しないファイルが
  除外されていないか確認できる
