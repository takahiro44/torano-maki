### 2026-08-27 AIチャット・ナレッジ検索が0件になる（knowledge_typeが正規化されていない）

- **やろうとしたこと**: AIチャットに「在庫が合わなくて顧客に謝ることになった事例は？」と質問した
- **起きたこと**: 「該当する事例がありません」と返ってきた。`/chat` のレスポンスの
  `tool_trace` を見ると `search_knowledge` が5回とも0件。一方、同じ文言を
  `/search` に直接投げると5件ヒットしていた（検索ロジック自体は壊れていない）

  ```json
  {"step":1,"tool":"search_knowledge","ok":true,"summary":"ナレッジを検索しました（0件）"}
  ```

- **原因**: `backend/app/services/agent_tools.py` の `search_knowledge` Toolは、
  Agentが明示しない限り既定で `knowledge_type=business` に絞り込む
  （2026-08-27 PR #45、`docs/decisions.md` 参照）。
  一方、2026-08-24作成の検証用JSON（`experiments/knowledge-extraction/output/meetings/*.json`）
  経由で投入したナレッジは `pain_point` / `sales_technique` 等の独自の細分類のまま
  DBに入っており、`business` / `casual` のどちらでもなかったため、絞り込みに
  一切ヒットしていなかった。`docs/decisions.md` の2026-08-26の決定では
  「既存データを一括UPDATEで統一した」とあるが、DBを作り直した／再投入した
  タイミングでこの正規化が失われていた
- **解決策**: 2026-08-27に `backend/scripts/normalize_knowledge_type.py` が
  main へマージされ、既存DBを安全に正規化できるようになっている
  （DELETEを伴わない単純なUPDATEなので、ロープレ等で参照済みの行があっても壊れない）。

  1. まず現状を確認する

     ```sql
     SELECT knowledge_type, count(*) FROM knowledge_units GROUP BY knowledge_type;
     ```

  2. `business` / `casual` 以外の値がある行の**中身を必ず目視確認する**（機械的に流さない）

     ```sql
     SELECT id, title, knowledge_type
     FROM knowledge_units
     WHERE knowledge_type NOT IN ('business', 'casual')
     ORDER BY knowledge_type, title;
     ```

     検証用JSON（`experiments/knowledge-extraction/output/meetings/`）だけを
     投入している場合は、全件が商談から抽出された営業ナレッジのため
     `business` に統一してよいことを確認済み。
     **自分で録音した音声や手入力など、検証用JSON以外のソースも投入している場合は、
     そのソース由来の行に casual 相当の内容が混ざっていないか特に注意して確認すること。**
     （`normalize_knowledge_type.py` は対象を無条件に `business` へ寄せるため、
     casual相当の行を先に個別で直しておかないと巻き込まれる）

  3. casual相当のものが見つかったら、その行だけ先に直す

     ```sql
     UPDATE knowledge_units SET knowledge_type = 'casual' WHERE id = '<該当ID>';
     ```

  4. 残りをまとめて正規化する

     ```bash
     cd backend
     uv run python scripts/normalize_knowledge_type.py --dry-run   # 件数確認
     uv run python scripts/normalize_knowledge_type.py              # 適用
     ```

  5. `/health/db` では検知できない。実際に `/chat` か `/search` へ同じ質問を
     投げて直ったことを確認すること

  **実機で確認済み（2026-08-27）**: `decision` のうち1件を一時的に `casual` に
  変更してから実行したところ、その1件だけは書き換わらずに残り、他118件のみ
  `business` になった。`/chat` に同じ質問を再度投げると、想定通り事例が返るように
  なった
- **未解決の場合**: `--dry-run` の対象が0件なのに症状が再現する場合、原因は

### 2026-08-26 ⚠️ TTSが本文ではなく「プロンプトを読み上げる」ことがある

- **やろうとしたこと**: 長編台本20本（845発話）を無人で音声化する
- **起きたこと**: `long_019` の22番目の発話（44字）だけ**27.7秒**あった。
  文字起こしすると、本文ではなく**プロンプトそのものを読み上げていた。**

  ```
  台本: 顧客業種、状況、質問、反応、次の行動をそろえると、別案件で使えるか判断しやすくなります。
  音声: これは日本企業で行われている法人営業の商談での営業担当者の発話です 話しては大塚商会
        高橋みさき30代女性です話す速度は普通で…（以下プロンプト全文）
  ```

  **エラーにはならない。** APIは成功を返し、WAVも正常に生成される。
  結合された音声を聴くまで気づけない
- **原因**: 不明。ただし**同じ発話で再現した**（作り直しても37.4秒になった）ため、
  偶発ではなく特定の本文で起きる。列挙で始まり指示のように読める文が疑わしい
- **解決策**: **合成した音声の長さを、本文の文字数から見込んだ長さと比べて検知する。**
  読み上げ速度は実測で4.4〜4.9字/秒なので、
  `見込み × 2.2` と `見込み + 6秒` の大きい方を超えたら失敗とみなし、
  既存のプロンプト差し替え（`synthesize_with_fallback`）で短いプロンプトを試す。
  実際にこれで9.5秒の正常な音声が得られ、文字起こしでも本文と一致した。
  `tts-demo/generate_tts.py` の `is_too_long` に実装済み
- **教訓**: **合成音声は「成功した」の確認だけでは足りない。**
  長さと文字数の比を見れば、聴かずに異常を見つけられる。
  `tts-demo/check_audio.py` で全パートを一括点検できる。
  845パート中、この1件以外に異常は無かった
- **注意**: 判定に引っかかっても不良とは限らない。列挙や言い淀みで3.2字/秒まで
  落ちることがあり、16件を文字起こしして確認したがすべて正常だった。
  **最終判断は文字起こし**（`experiments/stt` の環境を使う）

### 2026-08-25 ⚠️ PostgreSQL 標準の全文検索は日本語では使えない

**「全文検索を足そう」と思った人は先に読むこと。** 調整の問題ではない。

- **やろうとしたこと**: `tsvector` / `tsquery` / `ts_rank` で
  日本語ナレッジの Lexical Search を実装する
- **起きたこと**: **`tsquery` がそもそもヒットしない。**
  PostgreSQL の default parser は日本語を分かち書きできず、
  句点までを丸ごと1トークンにする（PostgreSQL 17.11 で実測）

  ```sql
  SELECT to_tsvector('simple', '基幹システム保守サービスの導入事例');
  -- → '基幹システム保守サービスの導入事例':1        ← 全体で1トークン

  SELECT to_tsvector('simple', '基幹システム保守サービスの導入事例')
         @@ to_tsquery('simple', '基幹システム');
  -- → f    （不一致）

  SELECT to_tsvector('simple', '当社の基幹システム保守サービス')
         @@ to_tsquery('simple', '基幹システム:*');
  -- → f    （前方一致でも、文の途中にあると不一致）
  ```

  `:*` による前方一致は「文の先頭から」しか効かない。
  `ts_rank` でスコアを見る以前の問題
- **原因**: `pg_ts_config` に日本語の設定が無い（29件すべて欧米言語＋`simple`）。
  分かち書き器も標準には含まれない
- **解決策**: **`pg_trgm` の `word_similarity()` を使う。**
  文字トライグラムなので分かち書きが要らない。
  `docker/initdb/01_init.sql` で有効化済み、`idx_knowledge_search_trgm` も
  DDL にあるので、**追加インストールもDB作り直しも不要**

  ```sql
  SELECT word_similarity('基幹システム', '基幹システム保守サービスの導入事例');
  -- → 0.857
  ```

- **`similarity()` ではなく `word_similarity()` を使うこと。**
  前者は文字列全体の長さで正規化するため、短いクエリを長い `search_text` に
  ぶつけると一致していても低い値にしかならない。
  後者はクエリに最も近い**部分列**を探す

  | 関数 | `'CloudLedger'` vs 該当ナレッジ全文 |
  |---|---|
  | `similarity()` | 0.088 ❌ |
  | `word_similarity()` | **0.750** ✅ |

- **注意**: 現在は `word_similarity(...) >= 閾値` を WHERE に書いており、
  **これは GIN インデックスを使わない**（関数呼び出しなので）。
  数十件規模では順次スキャンで十分速い。件数が増えたら
  `クエリ <% search_text` 演算子 + `SET pg_trgm.word_similarity_threshold`
  に書き換えるとインデックスが効く

### 2026-08-21 ⚠️ e5 の類似度スコアは絶対値で判断できない

**検索実装をする人は先に読むこと。**

- **やろうとしたこと**: `multilingual-e5-large` で日本語のナレッジ6件を埋め込み、
  自然文で検索して妥当な結果が返るか確認する
- **結果**: 妥当な結果が返る。ただし**スコアの読み方に注意が必要**と分かった

  | クエリ | 1位のスコア | 2位との差 |
  |---|---|---|
  | 値引きを求められたら | 0.868 | 0.056 ✅ |
  | サポート体制を重視する顧客 | 0.849 | 0.013 ✅ |
  | サポートを気にする顧客への対応 | 0.830 | **0.0002** ⚠️ |

- **分かったこと**:
  1. **スコアは 0.78〜0.88 の狭い範囲に固まる。**
     「0.9以上を関連ありとみなす」のような**絶対値のしきい値は機能しない。**
     順位（相対的な差）だけが意味を持つ
  2. **無関係な項目でも 0.78 程度は出る。** 低スコアだから無関係とは言えない
  3. 抽象的なクエリだと上位の差が 0.0002 まで縮まり、**順位が実質ランダム**になる。
     件数が少ないうちは特に起きやすい
- **検索を実装するときの指針**:
  - しきい値で足切りせず、`top_k` 件を返して人間に選ばせる
  - スコアをUIに出すなら「参考値」であることが分かる見せ方にする
  - 固有名詞（顧客名・製品名）の検索はベクトルだけだと弱い。
    `pg_trgm` のインデックス（`idx_knowledge_content_trgm`）を張ってあるので、
    必要なら併用する
- **性能（CPU / Windows x86_64）**: 6件の埋め込みが約0.4秒（モデル読み込み後）、
  検索1回が約0.2秒。**この規模ではCPUで十分**

### 2026-08-21 ベクトル検索は「同じ顧客の情報を漏れなく集める」のが弱い

15件のダミーデータでの評価結果（事前に固定した10問で **10/10 一致**）と、
そこで見えた弱点。

- **良好だったこと**
  - 固有名詞を含む具体的なクエリ（B社、CloudLedger、東都物流など）は
    該当項目が1位
  - 似た話題で結論が違う組（値引き2件、サポート2件）も、
    状況に合った方が1位になる
- **弱点1: 同じ顧客の全情報を集める再現率**
  「A社」という単語だけで検索すると、上位3件はA社だが4〜5位にB社・C社が混入し、
  **A社のセキュリティに関する項目は上位5件から漏れた**。
  1件を探す精度より、**漏れなく集める再現率**に問題が出る
- **弱点2: 特徴的な語に引きずられる**
  「情報システム部がしっかりしている会社」で検索すると、
  意図した「標準サポートで十分」ではなく、
  **「情報システム部の佐藤さん」を含む別のナレッジ**が1位になった。
  クエリ中の特徴語が、無関係なレコードの同じ語に引き寄せられる
- **対処の方針**: `pg_trgm` のインデックス（`idx_knowledge_content_trgm`）を
  張ってあるので、**キーワード一致の加点とベクトル順位を統合する
  ハイブリッド検索**が有効。次段階で検討する
- **無関係なクエリの扱い**: 「今日の天気」でも5件返り、1位のスコアは0.765。
  一方、有効な固有名詞検索でも0.796程度のことがあるため、
  **単純なしきい値で足切りすると有効な検索まで落とす。**
  画面側で「該当が無くても近い順に表示します」と明記する方針にした

### 2026-08-21 ⚠️ ネイティブPostgreSQLとのポート競合が「エラーなし」で起きる

**このリポジトリが既定で5432ではなく5433を使っている理由。**

- **やろうとしたこと**: バックエンドから `localhost:5432` のDBコンテナに接続する
- **起きたこと**: コンテナは healthy、コンテナ内の `psql` では接続できるのに、
  ホストからの接続だけが失敗する

  ```
  FATAL: ユーザー"torano"のパスワード認証に失敗しました
  ```

- **原因**: ホスト側でネイティブのPostgreSQLが5432で動いていた。
  **Windowsでは Docker とネイティブPostgreSQLの両方が5432をLISTENでき、
  「ポート使用中」エラーが出ない。** その状態でホストから接続すると
  ネイティブ側に吸われる。そちらに `torano` ユーザは存在しないため認証エラーになる

  ```
  $ netstat -ano | findstr :5432
  TCP  0.0.0.0:5432  LISTENING  18632   → com.docker.backend.exe
  TCP  0.0.0.0:5432  LISTENING   8080   → postgres.exe      ← これ
  ```

- **解決策**: 既定のポートを **5433** に変更した
  （`docker-compose.yml` / `.env.example` / `backend/app/config.py`）
- **注意**: 通常のポート競合と違い**エラーメッセージが「認証失敗」になる**ため、
  ポートの問題だと気づきにくい。認証エラーが出たらまず
  `netstat -ano | findstr :5433`（Macは `lsof -i :5433`）で
  何が掴んでいるか確認すること

### 2026-08-21 初期化SQLを追記しても反映されない

- **やろうとしたこと**: `docker/initdb/` にSQLを置いてDBを初期化する
- **起きたこと**: 一度起動した後にSQLを追記しても、再起動しただけでは実行されない
- **原因**: `/docker-entrypoint-initdb.d` のスクリプトは、
  **データディレクトリが空のとき（＝ボリューム新規作成時）にしか実行されない**仕様
- **解決策**: ボリュームごと作り直す

  ```bash
  docker compose down -v && docker compose up -d
  ```

  `-v` を付け忘れるとボリュームが残るため、何度やっても反映されない。
  **`-v` はデータを完全に削除するので、実行前に消えて困るデータがないか確認すること。**

### 2026-08-21 Windows の CRLF が `.env` に影響しないか検証

- **懸念**: Mac 2人 / Windows 2人の混在環境。Windowsで `.env` がCRLFになると、
  値の末尾に `\r` が混入して接続文字列が壊れる可能性がある
- **検証結果**: **問題なし。** Docker Compose v5.1.0 はCRLFの `.env` を正しく解釈し、
  値に `\r` は混入しなかった
- **ただし**: コンテナ内で実行される `.sh` / `.sql` はCRLFだと壊れるため、
  `.gitattributes` でLFを強制している。このファイルは消さないこと

### 2026-08-21 `.gitignore` の `models/` がスキーマ定義を巻き込む

- **起きたこと**: 大容量ファイル除外のつもりで `models/` と書くと、
  **`backend/app/models/`（Pydanticスキーマ定義）まで除外される**
- **原因**: 先頭に `/` が無いパターンは、どの階層のディレクトリにもマッチする
- **解決策**: リポジトリ直下だけを対象にする

  ```
  /models/
  /data/
  /uploads/
  /outputs/
  ```

- **確認方法**: `git check-ignore -v <パス>` で、意図しないファイルが
  除外されていないか確認できる
